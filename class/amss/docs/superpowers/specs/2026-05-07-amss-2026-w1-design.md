# AMSS 2026 — Week 1 Lecture Design

**Status:** Approved design (2026-05-07). Ready for implementation planning.
**Owner:** Traian-Florin Șerbănuță
**Parent spec:** `2026-05-01-amss-ai-redesign-design.md` (course-level redesign).
**Decomposition strategy:** Sequential by week. This spec covers Week 1 only; subsequent weeks each get their own spec → plan → implement cycle.

## Goal

Author the W1 lecture deck (`class/amss-2026/curs/01-intro.md`) plus its sibling demo runbook and fallback assets, replacing the current single-stub-slide placeholder. The deck plants the conceptual scaffold — architect-critic loop and the five course commitments — that the remaining 13 lectures rely on.

## Decisions (locked during brainstorm)

These apply to W1 specifically; some carry forward as course-wide conventions (called out where they do).

- **Language: English** for all lecture and lab decks. *Course-wide.* The project README stays Romanian to match the institutional student-facing context. CLAUDE.md updated to reflect this.
- **Demo policy: ≥1 live demo per lecture.** *Course-wide.* Live driving of the canonical agentic tooling against a small scenario, with a committed fallback (PNG screenshots) for when the network or model misbehaves.
- **W1 demo shape: mini end-to-end architect-critic loop.** Single cycle (architect prompt → AI output → critic walks defects → architect re-prompts → AI revises). Iteration as a recurring pattern lands later in Lab 1.
- **W1 demo scenario: library kiosk** (borrow + return + reserve). Familiar to all, structurally rich enough for a class diagram, naturally invites multiplicity and fabrication defects. Not reused in Labs 3-4.
- **Lecture spine: frame → demo → close.** Specifically: welcome → frame (architect-critic + 5 commitments) → demo → SDLC-changes deeper dive → tooling preview → logistics. Q&A folds into each segment organically rather than being a bulk buffer at the end.
- **Time budget: ~82 min content + ~15-18 min slack.** First lecture deliberately under-fills to absorb late arrivals, drop-ins, and longer logistics Q&A.
- **Lecture-shape: deck + sibling demo runbook.** Demo procedure lives in its own markdown file next to the deck. A reusable per-lecture template is *deferred* until W1's runbook exists in concrete form (premature abstraction otherwise).
- **SDLC-changes framing: "what AI does well / where AI fails"** per stage (rejected: binary "without AI / with AI").
- **F1+F3+F4 named three times** in the lecture — frame, SDLC-changes transition, and logistics. Deliberate repetition; the literacy floor is the spine of the entire course.
- **Verification: solo dry-run is always sufficient.** *Course-wide.* No group dry-run required for W1 or subsequent weeks.

## 2. Lecture spine, time budget, slide pacing

100-minute slot, ~82 minutes of planned content, ~15-18 minutes of natural slack. Q&A absorbed into each segment rather than buffered at the end.

| Segment | Time | Slides | Pacing peg |
|---|---|---|---|
| Welcome / who-am-I / agenda | 7 min | 2-3 | Light slides, ~2 min each, plus icebreaker chatter |
| **Frame: architect-critic loop + 5 commitments** | 20 min | 9-10 | 2 min/slide |
| **Demo: library kiosk, 1 cycle** | 12 min | 1 trigger slide + runbook | Slide stays up the whole demo |
| **SDLC-changes deeper dive** | 20 min | 9-10 | 2 min/slide; one stage per slide |
| Tooling preview | 8 min | 3-4 | 2 min/slide |
| Logistics | 15 min | 6-8 | 2-3 min/slide (Q&A-heavy in practice) |
| **Total** | **~82 min content** | **~30-35 slides** | + 15-18 min slack |

**Slide-density convention.** Bullet-light: no slide carries more than ~5 bullets, no bullet runs more than one line. Where a topic needs more text, it goes into the `::: notes` speaker block, not on screen. Diagrams (plantuml fenced blocks) are preferred to bullet lists wherever a structural relationship is the content. Pacing pegs: ~2 min per light slide; the demo trigger slide is 12 min on its own; UML-diagram slides are 3-4 min because students need read time. *Slide-density convention is course-wide.*

**Slide counts are budgets, not floors.** §4 below specifies the *required* slides per segment (the must-include content). The §2 ranges include ~1-3 slots per segment for elaboration the speaker chooses during authoring — e.g., an intro slide to a segment, a recap slide, an extra example. Required slides cover roughly 70-80% of each segment's count; the remainder is judgment.

## 3. Demo runbook contract

`curs/01-intro-demo.md` contains six fixed sections.

### 3.1 Setup (pre-class checklist)

Continue.dev open, pointed at the canonical course endpoint, in agentic chat mode. PlantUML rendering available (in-editor preview or terminal `plantuml -tpng -pipe`). Fallback PNGs queued in a tab. ~1 min before students arrive.

### 3.2 Architect prompt #1 (verbatim)

> *"Generate a UML class diagram in PlantUML for a small library kiosk. Users can borrow and return books. Staff can register returns. A book can be reserved while it is out on loan."*

Pasted as-is — no live improvisation. Reproducibility outweighs naturalness.

### 3.3 Defect catalogue (menu of 6, pick 2-3 live)

Each entry: defect description, slide-the-element-to-point-at, critique question for the room, architect-intent that exposes the defect. Catalogue (priority order, not all expected to appear):

1. **Multiplicity bug** — `User --1..1-- Loan` rather than `0..*`. Q: *"What if I'm borrowing two books at once?"*
2. **Fabricated class** — a `Library` class with no behavior, just a top-level container. Q: *"Read its methods aloud — what does this class actually do?"*
3. **Missing association** — `Reservation` linked to `Book` but not to `User`. Q: *"Who made this reservation? Walk the line back to the user."*
4. **Conflated concepts** — `Book` used for both abstract title and physical copy. Q: *"If two physical copies exist, can both be on loan to the same user?"*
5. **Missing guard / missing operation** — borrow without an availability check, or return without a state change.
6. **Anemic class** — `Staff` with no associations beyond a `register_return()` method.

Speaker picks the 2-3 that actually appear in live AI output. Over-spec'ing the catalogue is intentional — robustness against model variance.

### 3.4 Critique walkthrough (4-5 min)

Speaker walks the chosen 2-3 defects. The pedagogical move is named explicitly the first time: *"What I just did is the **critic** half of the loop. Now I'm going to do the **architect** half — I'll re-direct AI with what I learned."*

### 3.5 Architect prompt #2 (constructed live)

Template provided in the runbook:
> *"Update the diagram: [critique 1's correction], [critique 2's correction], [critique 3's correction]."*

The speaker fills the brackets from the chosen defects. ~1 min to type, ~1-2 min for AI to revise.

### 3.6 Recap and fallback

~1 min. Speaker recaps "we just did one cycle of the architect-critic loop" and points back at the two roles named in the frame. **Fallback** for live AI failure: switch to the queued PNGs (committed in `01-intro-demo-fallback/`) showing a previously-recorded run. The runbook calls this out explicitly so the speaker doesn't freeze.

### 3.7 Make-it-fail reserve

If AI produces a clean diagram with no critique surface (low probability for the kiosk prompt with current open-source models, but possible), the runbook supplies one fallback prompt: *"Now redo this for a system where books can be reserved by multiple users in a queue."* This near-certainly fabricates a `WaitingList` or similar with shaky semantics, restoring the critique surface.

### 3.8 Fallback assets

`01-intro-demo-fallback/` contains three committed PNGs:

| Filename | Contents |
|---|---|
| `01-fallback-cycle1-output.png` | Seed AI output for the kiosk prompt with at least 2 visible defects |
| `02-fallback-cycle1-revised.png` | Post-critique re-prompted output |
| `03-fallback-make-it-fail.png` | The make-it-fail reserve's output |

Captured during the solo dry-run (see §5). When the procurement decision changes the canonical endpoint, the dry-run reruns and the PNGs refresh.

### 3.9 Time budget reconciliation

The demo's 12-minute total decomposes roughly: setup (pre-class, not counted) + prompt #1 typed and submitted (~1 min) + AI generates (~1-2 min, dependent on endpoint) + critique walkthrough (~4-5 min) + prompt #2 constructed and submitted (~1 min) + AI revises (~1-2 min) + recap (~1 min) = 9-12 min. Variance lives mostly in AI generation latency; the runbook does not pad those moments — the speaker uses them to think aloud about what they expect.

### 3.10 Tooling-preview synergy

Because the demo runs Continue.dev pointed at the canonical course endpoint, students see the canonical tooling live before the explicit "tooling preview" segment. That segment can be a brief tour rather than a standing introduction.

## 4. Content contract per segment

For each segment, the **goal** (what students walk out understanding) and **required content** (must-include slides). Slide-by-slide bullets are an implementation concern, not a spec concern.

### 4.1 Welcome / who-am-I / agenda (7 min)

**Goal:** students know who is teaching, what today covers, and that this lecture is unlike the rest of the semester (front-loaded conceptual framing rather than dive into UML).

**Required content:**
- Instructor + course name slide.
- Agenda slide listing the spine sections.
- One-sentence "today is the framing day; week 2 is where the work begins" preview.

### 4.2 Frame — architect-critic loop + 5 commitments (20 min)

**Goal:** students can name both roles (architect/director, critic/reviewer) and recognize the 5 commitments as the shape of the rest of the course.

**Required content:**
- One slide naming the two roles (architect/director B, critic/reviewer A) — language tracks parent spec §1.
- Five slides, one per commitment, in the parent spec's order:
  1. AI is the default tool, not an exception.
  2. The trail is graded, not the running system.
  3. Implementation is a forcing function (TDD-with-AI), not a deliverable.
  4. Defensible literacy floor — F1 + F3 + F4 named explicitly.
  5. Tooling parity — same canonical setup for all.
- One handoff slide: "watch for these moves in the demo".

Each commitment slide carries one rule on screen plus a one-sentence rationale in `::: notes`. The slide is not the full argument; the speaker is.

### 4.3 Demo trigger (12 min)

**Goal:** students see one full cycle of the architect-critic loop end to end on a familiar scenario.

**Required content:** a single slide with the kiosk prompt visible, the runbook reference, and a "watch the architect move and the critic move" reminder. Speaker drives the runbook (§3) for the full 12 min.

### 4.4 SDLC-changes deeper dive (20 min)

**Goal:** students see concretely what AI does well and where it fails at each SDLC stage, and recognize that the rest of the semester traces these stages.

**Required content:** one slide per stage, framed as "what AI does well / where AI fails":
- Requirements gathering — previews W2.
- Test/spec design — previews W3.
- Structural modeling — previews W4-5.
- Behavioral modeling — previews W6-7.
- Patterns — previews W8-9.
- Quality / traceability / evaluation — previews W10-11.
- Coding — explicit one-line: "the parallel implementation course's domain, not ours; we use it as our forcing function via TDD."

Plus one transition slide tying these stages back to F1+F3+F4 (the literacy floor reappears — second of three mentions).

This segment doubles as an implicit syllabus walkthrough.

### 4.5 Tooling preview (8 min)

**Goal:** students know the canonical setup (Continue.dev + course endpoint), know where to find install instructions, and know the BYO rule.

**Required content:**
- "What you just saw" slide — refer back to the demo, name the components (Continue.dev in VS Code, the course endpoint).
- Pointer to `tooling/SETUP.md` and Lab 1 — explicit "we'll install together in Lab 1, don't try alone before then".
- BYO rule: Claude Code / Copilot / Cursor on personal accounts allowed *on top of*, not *instead of*, the canonical setup. Graded artifacts must reproduce on canonical.

### 4.6 Logistics (15 min)

**Goal:** students know schedule, grading, project shape, oral defense, resit exam, communication channel.

**Required content:**
- 14-week schedule with biweekly labs.
- Final grade: 8 (project) + 1 (attendance) + 1 (*din oficiu*) = 10.
- Project shape preview: teams of 3-5, domain announced 31 Oct, December checkpoint (Lab 5, 1 pt), final defense (W14).
- Oral defense rubric — F1 + F3 + F4 (third and final mention).
- Resit exam: R2 format, written, no AI, same competence as oral.
- Academic integrity pointer (one-page statement attached to syllabus).
- Communication channel placeholder (Teams link / email).

### 4.7 Deliberate omissions

Not in W1, by design:

- No UML notation teaching. The demo shows a class diagram but the lecture does not teach class-diagram notation — that's W4. UML in W1 is read intuitively, not formally.
- No deep-dive on any single SDLC stage — the deeper-dive segment surveys all of them; each gets its own week later.
- No design patterns, no specific UML diagram types beyond the demo's class diagram. Patterns are W8-9.

## 5. Verification

The lecture is "done" when all of:

1. **Pandoc build succeeds.** `make -C class/amss-2026/curs class/amss2026/curs/01-intro.html` and `01-intro.pdf` both produce well-formed output. No build warnings about missing `::: notes` blocks.
2. **Slide count and pacing match the budget.** Manual count totals ~30-35 slides; per-segment subsets fall within the §2 ranges.
3. **Frame's 5-commitment slides match parent spec §1 verbatim.** Each commitment's rule on screen matches the parent-spec wording. Drift is a correctness bug, not a style choice.
4. **Demo runbook is dry-run reproducible.** Instructor (you) runs the runbook end-to-end against the chosen course endpoint at least once before delivery; captures live AI output as the seed for the fallback PNGs; confirms the defect catalogue covers what the model actually produced. *This step blocks delivery.*
5. **Fallback PNGs exist** in `01-intro-demo-fallback/` per §3.8 (3 files, named as specified).
6. **`static/index.html` links resolve.** `class/amss2026/index.html` → `curs/01-intro.html` and `curs/01-intro.pdf` both load. (Already wired during scaffolding; reconfirm post-build.)
7. **Cross-reference linting.** Every reference in W1's slides to a future week names a session that exists in the parent-spec §2/§3 tables (titles match).

**Implicit dependencies:**

- Step 4 needs a working course endpoint. If procurement (parent spec §6) is still open at dry-run time, dry-run uses Gemini free-tier (option 2) and the fallback PNGs are captured from that. Lecture content does not change based on which endpoint is chosen — only the demo's actual output does.
- No automated test for slide content correctness. Editorial check ("does this teach what it should teach?") is judgment, not lint.
