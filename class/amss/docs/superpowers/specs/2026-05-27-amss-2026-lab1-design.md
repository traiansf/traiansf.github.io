**Decomposition strategy:** Sequential. This spec covers Lab 1 only; subsequent labs each get their own spec → plan → implement cycle.

## Goal

Author the Lab 1 student brief (`class/amss-2026/lab/Lab01.md`) plus an instructor runbook (`class/amss-2026/lab/Lab01-instructor.md`), replacing the current single-stub placeholder. Lab 1 is the onboarding lab and the hands-on follow-through of the W2 lecture: students drive AI to produce a requirements document for an assigned toy domain, critique it in pairs using W2's failure-mode vocabulary, iterate, and commit a requirements doc plus a 5-line reflection.

Lab 1 runs in the Week 2 lab slot. W2's lecture has already previewed this lab to students; **the deliverable contract is therefore locked** (see §3). This spec fills in mechanics only — it does not redefine what students hand in.

## Decisions (locked during brainstorm)

The "course-wide" tag marks decisions intended to carry forward to Labs 2-7.

- **Toy domain: single shared domain — vending machine.** Every pair works the same domain. Universally familiar (no domain-knowledge barrier), compact enough for a 60-min drill, and rich in obvious-but-unstated requirements (exact change, sold-out, simultaneous purchase, power loss mid-vend, refunds, restock/audit) so the critic half has real bite. A single shared domain makes the share-out a true side-by-side: ~50 pairs, same seed prompt, comparable failure-mode distribution. Not bike-sharing (the W2 demo domain), nor parking lot / ATM / drone CAS (reserved for Labs 3-4 per parent spec §3 and the 2025 lab catalogue).
- **Pair roles: swap each iteration.** Round 1: partner A architects (drives AI), partner B critiques. Round 2: swap. Both students practice driving AI *and* critiquing in one session, so F3 ("articulate why you directed AI") is drilled for both. Natural fit with W2's "iterate at least once" mandate. *Course-wide* default for paired drills unless a later lab needs fixed specialization.
- **Submission: branch push per pair.** Each pair pushes to a pair-named branch `lab01/<pair-id>` in the course lab repo. Lowest-friction path that still isolates pairs (no merge conflicts) and builds the clone → branch → commit → push habit. No pull request required for Lab 1 (PR-based review enters in later critique labs). *Course-wide* baseline; later labs may escalate to PRs.
- **Grading: completion + reflection gate (pass/redo, low-stakes).** Pass requires both deliverable files committed by deadline AND a reflection that correctly uses ≥2 named W2 failure modes and articulates a real prompting-move rationale (F3). A vacuous reflection (no named mode, no rationale) is a redo, not a fail. Onboarding lab — the bar holds on the literacy floor without scoring requirements-doc quality (which would wrongly reward AI output over critique skill).
- **Onboarding ≠ install.** Students arrive with Continue.dev pre-installed per `tooling/SETUP.md` (a ~30-min at-home task). The in-lab 15-min phase is credential setup + smoke test + git access, not installation. *Course-wide.*
- **No Java/TDD demo in onboarding.** The SETUP.md smoke test (`Ctrl+L → "summarize this file"`) is sufficient to confirm the endpoint. TDD-with-AI is W3 content, not Lab 1.
- **Two source artifacts, student/instructor split.** A published student brief plus an unpublished instructor runbook — mirroring the lecture pattern (published deck + unpublished `*-demo.md` companion). *Course-wide* pattern for labs, via a new `%-instructor.md` Makefile filter (§1).
- **Deliverable contract is not redefined.** Sourced from parent spec §3 row 1 and locked by W2's preview slide: "requirements doc + 5-line reflection on AI failure modes, committed to the lab repo." This spec specifies file names, a reflection template, and submission mechanics around that contract — nothing that changes what W2 already promised.

## 2. Session spine, time budget

100-minute lab slot. The 15 / 60 / 25 split is locked by parent spec §3 row 1 and echoed verbatim on W2's preview slide.

| # | Phase | Time | Owner | Notes |
|---|---|---|---|---|
| 1 | Tooling onboarding | 15 min | instructor-led | credentials + smoke test + git access; not install (§4) |
| 2 | AI-driven requirements drill (pairs) | 60 min | student pairs | two rounds, swap roles; vending machine (§5) |
| 3 | Share-out | 25 min | instructor-facilitated | side-by-side failure-mode tally (§9) |
| **Total** | | **100 min** | | no separate Q&A block — folds into onboarding + share-out |

The 60-min drill is the only compressible phase. Onboarding overruns (credential trouble) eat into drill setup, not the share-out — the share-out is the pedagogical payoff and is protected. §10 specifies how the drill degrades gracefully under time pressure (Round 2 is the buffer).

- **Slide "This Is What Lab 1 Drills"** (`02-requirements.md`): the three prompting moves — **scaffolded**, **role priming**, **negative prompting** — are what Lab 1 asks students to apply; *"Iterate at least once. Catch your own failure modes as you go; the 5-line reflection is where you name them."*
- **Slide "F1 + F3 + F4 — The Through-Line":** *"F3 (articulating why you directed AI a certain way) lands as you produce your own logs in Lab 1."*

What this lab inherits from W2 and must reuse, not reinvent:

- **The five named failure modes** students learned in W2's deck catalogue (`02-requirements.md` §5.6): **Fabrication**, **Over-Specification**, **Vague NFRs**, **Conflated Requirements**, **Fabricated Technology Choices**. These are the vocabulary the 5-line reflection must use. (W2's *live-demo* defect menu — spec §4.3 — listed six entries, splitting fabricated stakeholders from fabricated technology and adding "missing acceptance criterion"; but the titled, student-facing catalogue names the five above. Lab 1 keys off what students were *taught*, i.e., the five.) The vending-machine drill also surfaces a complementary lens the titled catalogue does not name — **omission** (requirements the AI simply left out, e.g., sold-out or power-loss handling). The brief introduces omission explicitly as the flip side of the catalogue (the five name what AI wrongly *includes* or *mis-states*; omission is what it *leaves out*), and reflection line 5 targets it.
- **The re-prompt scaffold** (W2 §4.5): *"Rewrite the requirements organized by use case. Each use case is one user goal. For each: who does it, what's the success criterion, and one realistic non-functional constraint. Drop fabricated stakeholders. - **The architect-critic loop** demoed on bike-sharing in W2 is the forerunner; students replicate it on the vending machine in pairs.

If any mechanic below would alter the deliverable as students heard it in W2, that is a spec error — flag it, do not silently diverge. (If a *future* revision genuinely needs to change the deliverable, W2's two preview slides need a synced one-line update.)

## 4. Tooling onboarding (15 min)

Students arrive with Continue.dev installed (SETUP.md done at home). This phase activates the endpoint and confirms repo access. Instructor-led, instructor floats to troubleshoot.

1. **0–5 min — distribute + configure.** Instructor hands out, per pair: the model-endpoint credentials (the three `REPLACE_BEFORE_W1` values — model, apiBase, apiKey), the pair-id, and the course lab-repo URL. Students paste the three values into `tooling/.continue/config.yaml`, replacing the markers.
2. **5–10 min — smoke test.** Open any file, `Ctrl+L`, prompt *"summarize this file"* (the SETUP.md smoke test). A coherent summary confirms the endpoint is live. Anyone who fails switches to the Gemini free-tier fallback (SETUP.md) or pairs on the working laptop (§10).
3. **10–15 min — git access.** Clone (or pull) the course lab repo, create branch `lab01/<pair-id>`, and push a one-line stub (e.g., create `lab01/<pair-id>/.gitkeep`) to confirm push access *before* the drill, so the only thing left at 50 min is committing real content. Instructor confirms each pair has a pushed branch.

Exit criterion for the phase: every pair has (a) a working AI completion in Continue.dev and (b) a pushed `lab01/<pair-id>` branch. Pairs that clear both early may start reading the drill brief.

## 5. The paired drill (60 min)

Domain: **vending machine.** Single shared domain for all pairs. Roles swap between the two rounds.

### 5.1 Setup (0–5 min)
Pair opens a working `lab01/<pair-id>/requirements.md`. Decide who is **A** (architect first) and who is **B** (critic first). Open a scratch `log.md` for the running prompt/critique log (optional deliverable, strongly recommended — it is the raw evidence behind the reflection's F3 line).

### 5.2 Round 1 — A architects, B critiques (5–30 min, ~25 min)
- **A** sends a deliberately under-scaffolded seed prompt (mirrors W2 demo prompt #1):
  > *"Generate a requirements document for a vending machine. Cover functional, non-functional, and domain requirements."*
- AI produces a flat draft. **B** critiques it against the six W2 failure modes, pointing at concrete instances and logging each (which mode, where). The vending-machine edge-case card (§5.5) is B's safety net if the draft looks suspiciously clean.
- **A** re-prompts applying the three moves — at minimum the use-case scaffold (W2 §4.5), optionally role-priming (*"act as a requirements engineer"*) and negative prompting (*"do not invent payment methods or hardware not stated"*). AI regenerates. **This re-prompt is the mandated "iterate at least once."**

### 5.3 Round 2 — swap: B architects, A critiques (30–50 min, ~20 min)
- **B** now drives, taking a fresh angle on the same domain — e.g., push for measurable acceptance criteria on each FR, or negative-prompt away the fabricated technology A's round surfaced. **A** critiques B's output against the same catalogue.
- Both keep the running log of *what they directed and why* — this is the F3 evidence and the source for reflection line 3.

### 5.4 Finalize + commit (50–60 min)
- Settle on the best `requirements.md` the pair drove the AI to (their tightest iteration, not the first draft).
- Write `reflection.md` — exactly five lines, per the §6.2 template.
- Commit both (and `log.md` if kept) to branch `lab01/<pair-id>`; push.

### 5.5 Vending-machine edge-case card (critic's safety net)
Given to students (not secret). If an AI draft looks complete, the critic stresses these reliably-missed cases — each maps to one or more failure modes:

| Edge case | Likely failure mode |
|---|---|
| Exact change unavailable / change-making | omission; or conflated requirements |
| Item sold out after selection | omission |
| Two buyers / concurrent selection of last item | omission; vague NFR (concurrency unspecified) |
| Power loss mid-vend (paid, not dispensed) | omission |
| Refund / cancel before dispense | omission; conflated requirements |
| Restock & cash audit (operator role) | omission (missing actor) — vs. fabrication if AI invents one |
| "The system shall be fast/reliable" | vague NFR |
| "Use an SQL database / specific coin mech" | fabricated technology |

(Note: most vending-machine gaps are *omissions* — the lens the catalogue's five named modes do not cover. That asymmetry is itself a teaching point: AI over-produces confidently and under-covers silently.)

## 6. Deliverable spec

### 6.1 Files (per pair, on branch `lab01/<pair-id>`)
- `lab01/<pair-id>/requirements.md` — the final AI-driven requirements doc (best iteration). Should cover functional / non-functional / domain requirements (mirrors the W2 demo's coverage). No length mandate.
- `lab01/<pair-id>/reflection.md` — **exactly five lines**, per §6.2. This is the graded literacy artifact.
- `lab01/<pair-id>/log.md` — *optional but recommended:* the prompt/critique transcript. Not required by the gate, but it is the concrete F3 evidence and helps the instructor adjudicate borderline reflections.

### 6.2 Five-line reflection template
The contract says "5-line reflection on the failure modes you observed." This template scaffolds those five lines onto the literacy beats (it does not change the contract — students may phrase freely, but each line should carry its beat):

1. **Worst failure mode** you observed, named from W2's vocabulary (one of the five named modes, or omission) + where it appeared. *(F1)*
2. **A second failure mode** + why it was easy or hard to catch. *(F1)*
3. **What you changed in the re-prompt and why** — which of the three moves, and the rationale. *(F3)*
4. **What improved (or didn't)** after iterating. *(F1 + F3)*
5. **One requirement the AI never got right** even after iteration — the residual risk. *(seeds F4: fabrications propagate downstream.)*

### 6.3 Pair-id scheme
Instructor-assigned, handed out with credentials (e.g., `p01`…`p50`). Documented in the instructor runbook so branch names and lab-repo directories are predictable and collision-free.

## 7. Lab repo structure + submission

The **course lab repo** (external, instructor-managed; URL handed out at lab start) is laid out:

```
lab01/
  README.md            # the brief — instructor commits before class (template in §11)
  p01/
    requirements.md
    reflection.md
    log.md             # optional
  p02/
    ...
```

- Each pair works on branch `lab01/<pair-id>` and pushes. No PR for Lab 1.
- Isolation by both branch *and* directory prevents cross-pair collisions even if a pair later merges.
- Instructor collects by listing remote branches (`git branch -r | grep lab01/`) and checking out each, or by viewing branches in the forge UI.

The student brief (§ student-facing content) gives the exact git command sequence so git-novice pairs can submit without instructor help:

```bash
git clone <lab-repo-url>      # (already done in onboarding)
git checkout lab01/<pair-id>  # branch created during onboarding (§4 step 3)
mkdir -p lab01/<pair-id>
# ...author requirements.md, reflection.md...
git add lab01/<pair-id>
git commit -m "Lab 1: <pair-id> vending machine requirements + reflection"
git push -u origin lab01/<pair-id>
```

## 8. Grading — completion + reflection gate

Low-stakes, pass/redo. Applied by the instructor against each pushed branch.

**Pass requires both:**
1. **Completion:** `requirements.md` and `reflection.md` both committed to `lab01/<pair-id>` by the deadline.
2. **Reflection gate:** the five lines (a) correctly name ≥2 distinct failure modes from W2's vocabulary (the five named deck modes, with *omission* also accepted as a valid mode), and (b) line 3 articulates a genuine prompting-move rationale (F3) — *why* the re-prompt was chosen, not just *what* was typed.

**Redo (not fail):** vacuous reflection — no named failure mode, or no rationale (e.g., "the AI was wrong, we fixed it"). The pair revises and re-pushes. The point is to enforce the literacy floor, not to punish.

**Explicitly not graded:** requirements-doc quality/length, AI output polish, number of iterations beyond the mandated one. Grading AI output quality would reward the wrong skill; this lab assesses critique and rationale (F1/F3), not generation.

The instructor runbook (§11) gives a worked example of a passing vs. a redo reflection so grading is consistent and fast across ~50 pairs.

## 9. Share-out (25 min)

The payoff of the single shared domain: same prompt, ~50 pairs, comparable failure-mode data.

1. **0–3 min — frame.** "Same domain, same seed prompt, ~50 pairs — let's see the failure-mode distribution across the room."
2. **3–18 min — 3–4 pairs present (~3–4 min each).** Each gives their **worst failure mode** + the **re-prompt move that fixed it** (or didn't). Pre-selected by the instructor during the drill from a quick scan of pushed reflections (aim for variety across the six modes), with one volunteer slot.
3. **18–23 min — live class failure-mode tally.** Hands-up per mode: "Whose AI fabricated a stakeholder? A technology? Wrote a vague NFR? Missed an acceptance criterion?" Instructor tallies on the board. This frequency data is only possible because everyone shared a domain.
4. **23–25 min — close.** Tie the tally to F1/F4: the modes you tallied are exactly what you critique every week; if requirements are fabricated, every downstream artifact (class diagrams in Lab 2, tests in W3) inherits the fabrication. Bridge to Lab 2.

## 10. Fallback plans

| Risk | Fallback |
|---|---|
| Course endpoint credential fails | Switch config to Gemini free-tier (SETUP.md); instructor keeps a few spare credentials. |
| Continue.dev broken on one laptop | Pair works on the partner's laptop — it is a pair lab; roles still swap, just on one machine. |
| `git push` fails (auth/network) | Submit by pasting both files into a shared doc / emailing the instructor; fix git after class. The deadline accepts the timestamp of the fallback submission. |
| Odd student count | One group of three: the third is a second critic in both rounds (and the log scribe). |
| AI output unexpectedly clean (little to critique) | Critic uses the §5.5 edge-case card to stress specific cases; a "too-clean" draft that silently omits these *is* the failure (omission). |
| Drill running long | Round 2 is the buffer. Minimum viable = Round 1 (which contains the mandated re-prompt) + reflection. "Iterate at least once" is satisfied by Round 1 alone. |
| Onboarding overruns past 15 min | Eats Round 1 setup, never the share-out. If onboarding is badly delayed, drop Round 2 for everyone and protect the 25-min share-out. |

## 12. Verification

Lab 1 is "done" when all of:

1. **Pandoc build succeeds.** `make -C class/amss-2026/lab class/amss2026/lab/Lab01.html` and `Lab01.pdf` both produce well-formed output.

3. **Student brief is self-contained.** A student reading only `Lab01.html` knows: the domain, the seed prompt, the two-round swap, the deliverable files + 5-line template, the git submission commands, and the grading gate — without needing the instructor runbook.
4. **Deliverable contract matches W2 verbatim intent.** The brief's deliverable = "requirements doc + 5-line reflection on failure modes, committed to the lab repo," with the 15/60/25 split. Cross-check against `02-requirements.md`'s two preview slides; any divergence is a spec error.
5. **Failure-mode vocabulary is consistent with what W2 taught.** The brief and reflection template name the same five modes as W2's deck catalogue §5.6 — Fabrication, Over-Specification, Vague NFRs, Conflated Requirements, Fabricated Technology Choices — plus the explicitly-flagged complementary *omission* lens. `grep` the brief for each term; confirm it does **not** present the spec-only "missing acceptance criterion" as if it were a taught catalogue mode.
6. **Three prompting moves named.** The brief names scaffolded / role-priming / negative prompting, matching W2's "This Is What Lab 1 Drills" slide.
7. **Domain is vending machine, not a reserved domain.** `grep -iE "parking|ATM|drone|bike" Lab01.md` returns no hits in the brief's drill content (a passing mention of "not your project" is fine).
8. **Cross-reference linting.** Every reference to a week or lab (W2 lecture, W3 testable specs, Lab 2) names a session that exists in parent-spec §2/§3.
9. **`static/index.html` link resolves.** `class/amss2026/index.html` → `lab/Lab01.html` and `lab/Lab01.pdf` both load.
10. **Git submission commands are correct.** The command sequence in the brief (§7) runs clean against a scratch repo (clone → branch → add → commit → push). *This step blocks delivery* — a broken submission recipe strands ~50 git-novice pairs.

**Implicit dependencies:**
- Step 1/2 need the lualatex toolchain (already restored during W2 work).
- No automated test for brief pedagogy; editorial judgment ("does this teach F1/F3?") is not lint.
- The course lab repo and credentials are instructor-side runtime inputs, not build artifacts; their existence is verified at lab time, not at build time.
