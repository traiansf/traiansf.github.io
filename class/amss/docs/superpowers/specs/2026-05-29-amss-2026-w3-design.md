## Goal

Author the W3 lecture deck (`class/amss-2026/curs/03-testable-specs.md`) plus its sibling demo runbook and fallback assets, replacing the current single-stub-slide placeholder. The deck delivers the four content threads the parent spec §2 mandates for W3:

1. Why tests are the executable form of requirements.
2. AI-generated tests as a spec-precision check.
3. The "if AI cannot produce a passing test from your spec, your spec is too vague" loop.
4. Traceability use case → scenario → test.

These are wrapped in **one architect-critic cycle on a bike-sharing fare requirement carried over from W2**, run live as a Python + pytest spec-precision loop.

W3 is a **lecture-only week** — labs are biweekly (Lab 1 was W2's week; Lab 2 is W4's week), so W3 has no lab slot. In place of a lab-synergy section, W3 seeds the project's required **TDD-with-AI reflection** deliverable (parent spec §4, per-student deliverable #4) and bridges forward to W4 (class diagrams) and Lab 2.

## Decisions (locked during brainstorm)

These apply to W3 specifically; the "course-wide" tag marks decisions inherited from W1/W2 that carry forward.

- **Spine: mirror W1/W2** — welcome → frame → demo → deeper-dive → close. *Course-wide* per-week template; reused unchanged.
- **Demo scenario: continue W2's city bike-sharing app.** The worked requirement is **fare calculation** — W2's demo left "users are charged for renting a bike" as a vague/missing-acceptance-criterion item; W3 makes that exact requirement executable. Maximum continuity: students watch one requirement mature from prose (W2) into an executable spec (W3), reinforcing the requirement → test trace.
- **Runtime: Python + pytest.** A pure function `fare(minutes) -> euros` and a pytest test that reads almost like the requirement. Lowest boilerplate; the test's readability *is* the pedagogical point ("tests are the executable form of requirements"). Diverges from the 2025 course's Java by design.
- **Loop emphasis: the test exposes a vague spec.** Architect-critic on the *spec*, not on code correctness. Cycle: vague requirement → AI writes a test that invents an unstated pricing rule → critique ("where in my spec is €0.10/min? it guessed") → tighten the requirement → AI writes tests that pin the behavior → AI writes code → tests pass. The "aha" beat is *the test caught my vague spec*. Code correctness is explicitly outside the course's grading scope (parent spec §4), so the demo centers spec precision, not TDD mechanics.
- **Slide density: bullet-light, ≤5 bullets, ≤1 line/bullet.** *Course-wide.* Inherited from W1.
- **F1+F3+F4 mentions: two — frame + close.** *Course-wide convention for content-weighted weeks* (locked in W2). F4 is the anchored mention: W3 is the first place the traceability chain gains its **executable tail** (use case → scenario → test).
- **Demo runbook contract: same 10-section structure as W1/W2's runbooks.** *Course-wide.* W3-specific content; adapted for a demo that *runs code* (env setup + terminal-visible run + pytest-output fallback assets).
- **Verification: solo dry-run is always sufficient.** *Course-wide.* Inherited from W1. W3 adds one hard gate: the reference pytest must actually run green during dry-run (§6).
- **No source-material reuse from AMSS 2025.** W3 is genuinely from-scratch. The 2025 testing lecture (`class/amss/curs/10-testing.md`) is reserved for W11 (model evaluation & quality) per parent spec §6, *not* W3. This is a deliberate non-reuse and is documented so future editors do not "restore" 2025 testing content here.

## 4. Demo runbook contract

`curs/03-testable-specs-demo.md` contains the same 10 fixed sections as W1/W2's runbooks — same structure, W3-specific content, adapted for a demo that executes code.

### 4.1 Setup (pre-class checklist, ~1 min)

Continue.dev open against the canonical course endpoint, agentic chat mode. A **terminal pane visible** (students must watch pytest run — the red→green moment is the point), plus an editor pane showing the test file as AI writes it. A scratch working directory with Python 3 and pytest already installed and verified. Fallback PNGs queued in a tab. Demo trigger slide on screen.

### 4.2 Architect prompt #1 (verbatim)

> *"Here's a requirement from last week's bike-sharing app: 'Users are charged for renting a bike.' Write a pytest test for the fare calculation."*

Pasted as-is — no live improvisation. The requirement is deliberately vague (no rate, no grace period, no cap), so AI must invent a pricing rule to write any concrete assertion. That invention is the demo's critique surface.

### 4.3 Critique catalogue (menu of 6, pick 2–3 live)

Each entry: how the AI-generated *test* fails, what to point at, critique question for the room. Over-spec'ing the catalogue is intentional — robustness against model variance.

| # | Test failure mode | Where to point | Critique question |
|---|---|---|---|
| 1 | **Invented assumption** | Test hard-codes a rate the spec never stated (`assert fare(60) == 6.0`) | *"Where in my spec is €0.10/min? It guessed — and a teammate's AI would guess differently."* |
| 2 | **Trivially-passing test** | Assertion that holds for almost any implementation (`assert fare(10) >= 0`) | *"Does this test fail for any wrong implementation? If not, it proves nothing."* |
| 3 | **Tautological / circular** | Expected value computed the same way the code computes it | *"If the code and the test share the same bug, the test still passes. Useless."* |
| 4 | **Missing boundary** | No test for 0 minutes, exactly the grace cutoff, or a daily cap | *"What happens at exactly 30 minutes? The spec — and the test — are silent."* |
| 5 | **Faithfully encodes a wrong spec** | Test correctly encodes unbounded per-minute charging (no cap) | *"The test matches the spec exactly — and the spec is the thing that's wrong."* |
| 6 | **Happy-path only** | No negative-duration / invalid-input case | *"What should `fare(-5)` do? Neither the spec nor the test says."* |

Speaker picks the 2–3 that actually appear in live AI output. #1 is near-certain given the vague prompt and should anchor the walkthrough.

### 4.4 Critique walkthrough (~5 min)

Speaker walks the chosen 2–3 failures. The architect/critic move is named explicitly the first time, framed *on tests*:

> *"That's the **critic** half — reading the test AI wrote and asking 'does this actually pin the behavior I want?' The answer is no, because my spec never said what the fare is. Next is the **architect** half — I tighten the spec and re-prompt."*

### 4.5 Architect prompt #2 (constructed live, tightened spec)

Template provided in the runbook:

> *"Refine the requirement: renting is free for the first 30 minutes, then €0.10 per minute, capped at €5 per calendar day. Now write pytest tests covering: a 20-minute ride (free), a 90-minute ride, exactly 30 minutes (boundary), and a ride that hits the daily cap. Then write the `fare` function and run the tests."*

The tightened spec is the pedagogical pivot: the *same* AI now writes tests that pin the behavior, because the requirement finally says what "charged" means. ~1 min to type, ~2–3 min for AI to generate tests + code + run.

### 4.6 Recap (~1 min)

> *"One architect-critic cycle on a testable spec. The first pass produced a test that looked fine but secretly invented the price — the critic half caught that the spec was too vague to test. The architect half tightened the requirement, and the second pass produced tests that actually pin the behavior, then code that passes them. That loop — if AI can't write a passing test from your spec, your spec is too vague — is the method your project's TDD-with-AI reflection asks you to run."*

Points back to the loop diagram from §5.6 and forward to the project hook (§3).

### 4.7 Make-it-fail reserve (inverted)

For this demo, the *desired* outcome is the vague-spec exposure, not a green test. The reserve handles the opposite risk: AI's first test guesses a *reasonable* pricing rule and looks correct.

> *"Notice it picked €0.10 per minute with a free first half-hour. Reasonable — but my spec never said that. Three teammates' AIs would pick three different rules, and all their tests would pass. That's exactly the problem: the test is only as precise as the spec behind it."*

The spec-precision lesson lands even without a red test — the guess *is* the evidence. If the speaker wants a visible red→green anyway, prompt #2's boundary/cap tests reliably fail against the first guess's implementation.

### 4.8 Fallback assets

`03-testable-specs-demo-fallback/` contains committed PNGs captured during the solo dry-run:

| Filename | Contents |
|---|---|
| `01-fallback-cycle1-test.png` | AI's cycle-1 test from the vague prompt, showing the invented-assumption defect |
| `02-fallback-cycle2-tests.png` | AI's cycle-2 tests + `fare` function from the tightened spec |
| `03-fallback-pytest-green.png` | Terminal showing pytest run passing (the red→green payoff) |

A fourth optional PNG (`04-fallback-pytest-red.png`, the boundary/cap tests failing against the cycle-1 guess) may be captured if the speaker plans to show an explicit red state. When the procurement decision changes the canonical endpoint, the dry-run reruns and the PNGs refresh.

### 4.9 Time budget reconciliation

Prompt #1 typed (~0.5 min) + AI generates test (~1–2 min) + critique walkthrough (~5 min) + prompt #2 typed (~1 min) + AI generates tests + code + runs pytest (~3–4 min) + recap (~1 min) = ~12–14 min. Variance lives in AI generation latency and pytest run time; the runbook does not pad those moments — the speaker uses them to predict aloud what the test should assert before it appears.

### 4.10 Project synergy

The demo is the in-lecture instance of the loop each student runs for the project's required TDD-with-AI reflection (parent spec §4, per-student #4). The runbook's prompt-#2 pattern (tighten the spec with measurable rules → re-prompt for boundary-covering tests → run) is the method the reflection documents. Unlike W2's runbook, there is no same-week lab to feed; the synergy is to the project deliverable.

## 5. Content contract per segment

For each segment, the **goal** (what students walk out understanding) and **required content** (must-include slides). Slide-by-slide bullets are an implementation concern, not a spec concern.

### 5.1 Welcome / agenda (3 min)

**Goal:** students know what today covers and how it connects to W2.

**Required content:** one agenda slide listing the spine + the one-line "last week we elicited requirements; today we make them testable."

### 5.2 Frame — from requirements to testable specs (8 min)

**Goal:** students recognize that a requirement can look complete and still be untestable, and recognize F1+F3+F4 as the rubric for the course.

**Required content:**
- "Recap: architect + critic" slide — both roles named again (1 line each); cite W2.
- "A requirement that looks fine until you test it" — show W2's "users are charged for renting a bike" and ask what a test for it would assert. The gap is the hook for the whole lecture.
- "Four threads in today's lecture" — preview tests-as-requirements, spec-precision check, the vague-spec loop, traceability.
- F1+F3+F4 anchor slide (1st of 2) — point at F1 (today you critique AI-written *tests*) and F4 (the trace gains a new terminal node: the test).

### 5.3 Demo trigger (15 min)

**Goal:** students see one full architect-critic cycle on a testable spec and the "the test caught my vague spec" moment live.

**Required content:** single slide with the vague fare prompt visible, runbook reference, "watch what price the AI invents — my spec never said" reminder. Speaker drives the runbook (§4) for ~12–14 min.

### 5.4 Tests as the executable form of requirements (10 min)

**Goal:** students can state that a test is a requirement you can run, and map an acceptance criterion to an assertion.

**Required content:**
- "A test = a requirement you can run" definition slide.
- "Acceptance criterion ↔ assertion" — side-by-side: a prose acceptance criterion next to the pytest assertion that encodes it (reuse the demo's fare example).
- "Vague requirement → no test possible" — the contrapositive: if you cannot write the assertion, the requirement is underspecified. This is the lecture's mantra in its constructive form.
- One slide distinguishing *executable* spec (test) from *documentation* spec (prose) — both are specs; the test is the one that fails loudly when violated.

### 5.5 AI-generated tests as a spec-precision check (12 min) — central payload, part 1

**Goal:** students can name how AI-written *tests* fail and critique them on sight (this is F1 applied to tests).

**Required content:**
- One slide per core failure mode (invented assumption, trivially-passing, tautological), each with: name, 1-line definition, realistic pytest snippet, critique question.
- One slide extending to secondary modes (missing boundary, faithfully-encodes-wrong-spec).
- One transition slide tying these to the demo students just watched ("you saw mode #1 — invented assumption — live in cycle 1").
- A one-line plant for W11: AI checking its own output against its own tests is a weak evaluator. No slide of its own; lives in `::: notes` or one bullet.

### 5.6 The "vague spec" loop (12 min) — central payload, part 2

**Goal:** students internalize the iterative loop and the mantra "if AI can't write a passing test from your spec, your spec is too vague."

**Required content:**
- **One canonical loop diagram** (the takeaway slide): spec → AI writes test → critique (does it pin behavior?) → tighten spec → repeat until the test encodes intent → AI writes code → run. Rendered as a simple flow (plantuml/graphviz allowed; this is a *process* diagram, not UML structural notation).
- "The mantra" slide — the sentence stated plainly, with the demo as its proof.
- One slide on convergence: the loop terminates when the test stops surprising you, not when the code is "done."
- One slide warning that AI will happily loop forever producing plausible tests — the *human's* judgment ("does this test express what I actually want?") is what closes the loop. Reinforces the architect-critic ownership.

### 5.7 Traceability: use case → scenario → test (12 min) — F4

**Goal:** students understand that the test is the executable tail of the traceability chain, and can walk requirement → use case → scenario → test.

**Required content:**
- "The chain gains a tail" slide — the W2 chain (requirement → use case) extended: use case → **scenario** → **test**.
- "Scenario = a concrete instance of a use case" — one user goal, one concrete path through it; the scenario is what becomes a test case (the fare example: the use case "rent a bike," the scenario "90-minute ride," the test `test_fare_90_min`).
- "Test = scenario made runnable" — the binding that makes traceability *verifiable*, not just documented.
- One slide on broken-link critique (foreshadowing W10): a test that asserts behavior no requirement asked for is an orphaned link, same as a fabricated requirement.

**The trace chain here is a process/dependency chain, not UML class or structural notation** — see §5.9 and the §6 verification guard.

### 5.8 Bridge to W4 + Lab 2 preview + project TDD deliverable + close (10 min)

**Goal:** students know how W4 reframes the loop toward structure, where Lab 2 picks up, and that this lecture's loop is their project's required TDD-with-AI reflection.

**Required content:**
- Project hook slide — "the loop you saw today *is* your TDD-with-AI reflection deliverable" (parent spec §4, per-student #4): run it on one feature of your slice, document what the failures revealed about your spec. Note that code is a byproduct; the reflection is what's read.
- W4 teaser — once a requirement is pinned by a test, what objects realize it? Class diagrams (W4) supply the structure behind the behavior.
- Lab 2 pointer — next hands-on slot is W4's lab (class-diagram drill); mechanics in Lab 2's own brief.
- F1+F3+F4 anchor slide (2nd of 2) — explicitly anchor F4: the test is the end of the traceability chain; if you cannot trace a test back to a requirement, the chain is broken.
- Closer slide — "next week: class diagrams; the method you saw today is the one your project reflection documents."

### 5.9 Deliberate omissions

Not in W3, by design:

- **UML class / structural notation.** W4 owns this. W3 stays at behavior/spec level; the only diagram is the §5.6 process loop and the §5.7 trace chain, neither of which is UML structural notation.
- **TDD ceremony / framework depth** (fixtures, mocking, parametrization beyond a single `@pytest.mark.parametrize` if it appears, CI integration). W3 teaches *testable specs*, not pytest mastery. Mechanics stay minimal.
- **Test coverage metrics, mutation testing, property-based testing.** Out of scope; coverage/quality evaluation is W11's lens, and even there only conceptually.
- **Code grading / "make the code good."** Parent spec §4: code is a byproduct, never graded. The demo runs code only to show red→green; correctness of `fare` beyond passing the tests is not discussed.
- **Sequence/state diagrams as test realizations.** Behavioral UML is W6/W7; W3's "scenario" is prose + test, not a diagram.
- **Bullet-by-bullet slide authorship.** Implementation, not spec.
